# Epic 04 — Session Management

## Responsibility

This epic owns **device sessions and their lifecycle**:

- creating a session per login (`auth_sessions` row, id = JWT `sid`)
- storing **only the SHA-256 hash** of each session's current refresh token
- session validity (not revoked, not expired, owned by `sub`)
- refresh validation, compare-and-swap rotation and **reuse detection**
- revocation: one session, all sessions, all except current, and the reasons
- the user's own device endpoints: `GET /auth/sessions`, `DELETE /auth/sessions/:id`, `POST /auth/sessions/revoke-others`

## Does Not Own

| Concern | Owner |
|---|---|
| Token claims/signing, the `/auth/refresh` endpoint | [03](./03-jwt-and-tokens.md) |
| Logout / logout-all use cases (they call this epic) | [01](./01-authentication-and-access.md) |
| Admin revocation of another user's sessions (HTTP) | [05](./05-admin-management.md) |
| Table DDL and migrations | [08](./08-database.md) |

## Objective

Support many devices per user, let each be signed out individually, and detect and contain stolen refresh tokens.

```
User
 ├── Chrome / Windows   (session A)
 ├── Android            (session B)
 └── iPhone             (session C)   ← revoke C without touching A or B
```

## Session entity (`auth_sessions`)

| Field | Meaning |
|---|---|
| `id` | UUID generated by the app before signing, embedded as `sid` |
| `user_id` | owner (FK, cascade delete) |
| `refresh_token_hash` | SHA-256 hex of the **current** refresh token (replaced each rotation) |
| `expires_at` | = current refresh token `exp`; moves forward on rotation |
| `revoked_at`, `revoked_reason` | revocation (terminal; both set or both null) |
| `last_used_at` | last successful refresh |
| `ip_address`, `user_agent` | device info captured at login |
| `created_at`, `updated_at` | timestamps |

**Raw refresh tokens are never persisted.**

## Requirements

| ID | Requirement |
|---|---|

| FR-REFRESH-02..06 | Validate session state and hash; rotate atomically; reuse revokes |
| FR-LOGOUT-03/04 | Revoked sessions reject both token types. The service offers `revoke`, `revokeAllForUser`, `revokeAllExcept`. |
| FR-S-01..03 | Own sessions: list (with `current` flag), revoke one (404 if not owned), revoke others |
| FR-S-07 | Ended sessions are purged after 30 days (epic 10 runs it) |

## Business rules

1. A session is **usable** iff `revoked_at IS NULL AND expires_at > now()` and its user is `ACTIVE`.
2. Revocation is terminal and keeps the **first** reason.
3. **Reuse detection:** a validly signed refresh token whose hash is not the session's current hash means an old token is being replayed. Revoke **that session** with `REUSE_DETECTED`, log `auth.refresh.reuse_detected`, return 401. Other devices are unaffected.
4. **Concurrent refresh** with the same token: the compare-and-swap lets at most one win. The loser is treated as reuse, so the session is revoked (strict policy). Clients must serialize refreshes.
5. Refresh by a non-active user revokes the session with `USER_NOT_ACTIVE` and returns 403.
6. Users can only see and revoke their own sessions. Foreign ids return 404, never 403.

| Reason | Set by |
|---|---|
| `LOGOUT` | `/auth/logout`, `DELETE /auth/sessions/:id` |
| `LOGOUT_ALL` | `/auth/logout-all` |
| `LOGOUT_OTHERS` | `/auth/sessions/revoke-others` |
| `REUSE_DETECTED` | refresh with a non-current token / lost rotation race |
| `USER_NOT_ACTIVE` | refresh while the user is not ACTIVE |
| `ADMIN_REVOKED` | `DELETE /users/:id/sessions` (epic 05) |

## Technical rules

- Access-token check = **one query**: session ⨝ user ⨝ roles (`SessionsRepository.findActiveIdentity`). Non-UUID ids are rejected before querying.
- Rotation SQL: `UPDATE … SET refresh_token_hash = new WHERE id = sid AND refresh_token_hash = current AND revoked_at IS NULL AND expires_at > now()`. 1 row = rotated, 0 rows = reuse.
- Hash comparison uses `crypto.timingSafeEqual`.
- All revocation UPDATEs include `AND revoked_at IS NULL`.

## API behaviour

| Endpoint | Auth | Success | Errors |
|---|---|---|---|
| `GET /auth/sessions` | access token | `200 { items: [{ id, current, ipAddress, userAgent, createdAt, lastUsedAt, expiresAt }] }` | 401, 403 |
| `DELETE /auth/sessions/:id` | access token | `200 { revokedSessions: 1 }` | 400 (bad UUID), 401, 403, 404 |
| `POST /auth/sessions/revoke-others` | access token | `200 { revokedSessions: n }` | 401, 403 |

Hashes and revocation internals are never exposed.

## Security considerations

- A DB leak exposes only hashes, which cannot be replayed.
- Revocation is effective immediately for access tokens, because every request checks the session.
- `ip_address` / `user_agent` are personal data: they are shown only to their owner (and admins) and purged with the session.

## Acceptance criteria

- [ ] Two logins create two sessions. The DB holds the SHA-256 of the refresh token, never the token.
- [ ] Rotation replaces the hash, keeps `sid` and extends `expires_at`.
- [ ] Reusing a rotated token revokes the session and kills the newer tokens too.
- [ ] Concurrent refreshes produce at most one success and a revoked session.
- [ ] Own-session list flags the current one. Foreign ids return 404. Revoke-others keeps only the current session.
